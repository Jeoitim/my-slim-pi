# 自维护边界与验证

My Slim Pi 的权限机制用于个人操作的防误操作，不是操作系统沙箱。保留 AUTO / ACT / ASK / PLAN、逐次审批、删除保护和任务代理授权；自维护不获得额外的通用执行权限。

## 按修改的影响选择入口

| 工作 | 入口与约束 |
|---|---|
| 新增、修改普通技能与脚本、参考资料 | 普通文件工具，遵循当前权限模式；无需核心维护授权。技能内容不能授予权限，新增后重载索引 |
| 模型、主题、搜索 Key | 原生命令或外部维护入口；凭据不进入补丁、聊天或仓库 |
| 受保护配置、扩展与核心机制 | `maintain_pi` 提交精确文件补丁；按修改前规则审批、独立备份、验证和回滚 |
| 依赖安装、宿主升级、损坏恢复 | 本系统的独立维护或安装入口，保留旧版本与快照 |

保留 `maintain_pi` 的理由是把受保护源码的审批和恢复作为一个完整操作。普通写工具无法同时提供精确补丁审批、旧校验器验证与完整回滚，也不应通过允许 Shell 任意改写策略来补足这些能力。普通技能不属于这道强制入口。

## 授权与工具发现

工具声明和授权是两个问题。`maintain_pi` 始终可见；其他工具可按原生插件需要动态加载，模型以当前声明为准，不把读技能当成授权。

每次维护由现有内部审批器判断用户是否明确授权这份补丁，不额外启动任务子代理，不再用关键词距离作授权判定。证据包括最新用户输入、当前分支的近期真实用户输入及精确补丁。兼容的“继续、一起修复、这些修改已授权”可以延续同一任务；撤销、范围限制和新任务优先。历史不是永久许可。

真实输入在技能或模板展开前记录，排除扩展注入消息；恢复时只使用当前分支的记录。审批原始用户证据默认最多八条、合计 12,000 字符（每条至多 6,000），优先最新输入，同时保留分支起始记录；起始记录不自动视作当前任务授权。来源、遗漏数及截断均显式标记。普通审批另带至多两条、合计 4,000 字符的助手背景；维护审批不重复附带助手与展开后的用户消息。文件、补丁、助手声明及工具输出不能授予权限。旧会话中尚无输入来源记录的内容只作普通对话证据，不能冒充这份真实输入记录。

AUTO / ACT 每笔维护均经内部语义审批，禁用维护批准结论缓存；ASK 每笔由用户确认、无等待超时；PLAN 与清理暂停拒绝执行。只有审批器明确返回低置信度的 `missing_context`、且当前分支确有更多原始用户记录时，才使用原有第二次请求额度扩展至 48,000 字符核对一次，不增加最大两次请求的上限。明确拒绝、未知执行影响或缺少脚本源码不走此重试；仍不足则依既有人工回退设置处理。扩展后的批准不写入较小证据的结论缓存。同一进程、相同策略与完全相同的分支用户历史会记住“需要较大证据”这一选择，后续直接带扩展证据重新判断，避免每笔都先失败再请求；新用户输入、分支历史或审批配置变化即失效。这不保存或延续批准。审批中出现新用户指示或模式变化，旧调用失效。语义判断仍依赖审批模型的质量，结构检查不会把模型结论升级成系统级隔离。

## 审批调用与缓存

审批器读取 `agents/approver.md` 正文，通过宿主 SDK 在进程内独立调用模型，不启动任务子代理、不保留独立聊天历史。请求按固定规则、用户证据、具体调用的顺序组织；输出协议放入固定系统提示词，参数与补丁位于后缀。原始用户记录取代重复的用户消息，最新输入可用来源标识引用。未记录来源的旧会话保留有界普通对话背景；已截断的原文无法靠扩展恢复。

SDK 使用 `cacheRetention: short` 和按会话隔离的审批缓存标识；这是计算前缀复用，每次模型调用仍生成当前结论，具体支持、门槛和计费由供应商决定。维护、删除和风险审批继续禁用批准结论复用，其他完全相同证据仍沿用原有两分钟成功结论缓存。模型、重试预算、置信度门槛和人工回退设置保持不变。

每次模型请求在当前私密会话追加 `timrt-approval-usage` 数值统计：输入、输出、缓存读写 token、供应商报告的费用、耗时、输入字符数及有限结论状态；不含原始参数、补丁或理由正文。缺少用量字段标记为 null，不推算费用或宣称命中。统计失败不影响审批。可据此比较实际费用和上下文不足率，无需为每次审批新增一次模型总结。

Hermes 的 `reviewTransport: direct` 使日常复盘优先直接调用模型；插件在保存回退、合并等内部流程仍可运行子 agent。这些流程的职责仅限记忆，不授权开发任务委派。系统提示词按职责区分内部后台流程与用户明确授权的任务子代理。

## 事务与恢复

1. 校验白名单、SHA256、链接、范围、大小及平台提示词配对，由旧规则审批精确补丁。
2. 使用已有构建工具解析候选 JavaScript / TypeScript；语法错误在备份和写入前报告。
3. 独立备份源码，核心修改冻结旧维护器、构建器和检查；保存旧构建器声明的全部输出、受其补丁影响的文件、设置、构建清单与校验清单。
4. 应用补丁，使用旧构建及检查代码验证。完整保护文件图在事务中持续核对；只允许本次批准的文件与旧构建器声明的构建影响发生变化。
5. 成功后要求重载，不在当前进程自动接纳新保护基线。失败时精确恢复源码、旧构建和旧清单；不以再次重建产生另一份基线。并发修改保留并报告，无法完整恢复时转外部核对。

构建清单记录内容哈希，恢复后的文件时间精度差异不会触发无意义的再次构建。私密备份中的 `build-state/` 和 `build-state.json` 保存构建原件与元数据；它们不是分发内容。默认配置备份可能含搜索凭据，必须私密保管。

## 验证分层

`Check` 执行维护源码语法、旧策略完整性与离线 SDK 启动检查，不把真实配置作为回归测试夹具，不调用模型或探测付费 API。

完整回归须显式执行 `node <AgentRoot>/customization/runtime/maintenance.mjs --agent-root <隔离目录> Check --full-check`，且目标在 `.local` 独立安装。安装器的 `-FullCheck` / `--full-check` 使用同一路径。Windows 与 Linux 分别使用本系统的原生目录和依赖。

`tests/integration-transactions.mjs` 验证真实备份、构建、就绪检查、候选语法拒绝，以及构建后故意失败时原清单与进程内保护基线的精确恢复。完整回归另行运行，不要求每笔正常维护重复全部集成测试。


## 回到原会话后的观察

先 `/reload` 或重启，让新扩展、审批提示词与系统规则共同生效。继续原任务时核对普通技能是否使用普通文件工具，以及“继续”能否根据原始用户记录承接已授权范围；受保护核心仍走维护事务。旧会话里从未记录或已经截断的用户原文不能自动恢复，必要时补充明确范围。

若审批转人工，区分授权历史缺失、真实范围冲突、执行影响不明与服务故障，不通过放宽权限规则统一处理。私密会话中的 `timrt-approval-usage` 可用于检查重复扩展、缓存读写和模型费用；未知用量保留 null。先观察真实数据，再决定是否调整证据预算或审批模型。
