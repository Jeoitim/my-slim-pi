## pi-tidy 集成验收

pi-tidy 0.4.11 使用原生入口和宿主 SDK，两端各增加一个发布包，没有运行依赖或执行工具。按用户选择，pi-cc mode=off，让出工具分组和边框；启动页等独立功能及本地 composer 保留。设置 tidy.alwaysShowTools 包含 edit/write/replace/insert。

两端的真实 SDK 组件回归在 TUI 上下文中同时加载完整 suite、pi-cc 和 pi-tidy，验证单入口、无执行工具注册、ccstyle 与任务授权命令保留、两个 read 折叠成一条摘要、展开后显示两份结果，以及 replace 编辑独立显示圆角框。全部既有权限与问答回归继续通过；没有修改第三方源码。测试使用组件和模拟 UI，不宣称完成真实终端鼠标拖动的人工验收。

安装前分别私密备份 settings、npm 清单/锁文件及 pi-cc 配置；实际目录仅增加 pi-tidy 并调整已确认的渲染配置，没有更新其他包。安装后执行离线启动与 Check，并核对认证、模型、信任、记忆配置、搜索配置及权限/委派配置保持原值。源码通过白名单导出同步，不导出个人状态。

## 原生更新验收

在两端的独立夹具中，从 Pi 1.3.0 运行原生 pi update --self 激活已经安装的 1.4.0，再检查普通启动。另使用只装 1.3.0 的独立目录，验证原生更新器下载官方安装清单、在 staging 中安装 1.4.0、切换 current-version，并执行 --version；未修改上游更新器。

插件验收直接运行带 --save-exact、--legacy-peer-deps、--ignore-scripts 的 npm install，随后通过 stdin 关闭的普通 RPC 启动触发自动重建，无模型请求。核对 settings 版本与实际安装包一致、编译有效性和策略完整性均通过。原生下载测试使用本机已有代理，不保存新代理配置、不修改用户 PATH。

## 实际部署与数据保护

Windows 和 Linux 的实际 AgentRoot 均完成安装更新；两端分别在私密配置快照中保存旧 npm 清单、锁文件及核心源码，并对 Hermes 会话索引库和 Hashline 撤销库执行 SQLite 在线备份。旧宿主 1.3.0 保留。

部署前后核对模型、认证、信任、平台规则、代理角色、主题、快捷键、模型/后台模型选择、Web 配置、旁聊配置、权限与持续委派配置，均保持原值。Hermes 新增 usageHitTrackingEnabled=false，搜索不启用命中计数写入；Hashline 首次配置 undoRetentionDays=0，避免新默认期限清理旧撤销记录。已有明确期限保留。

就绪报告保存在各自 AgentRoot 的 customization/reports/version-update.json。实际目录仅执行离线启动与就绪检查，不作为回归夹具；没有发起真实模型或收费搜索请求。自动审批的语义质量及供应商网络稳定性不由这些离线测试保证。宿主和扩展已在磁盘更新，原会话需退出并重新启动 Pi。

## 平台与恢复边界

Windows 使用原生 powershell，Linux 使用原生 bash；安装器部署对应的 APPEND_SYSTEM.md，保留已有个人规则和默认工具。WSL 不复用 Windows AgentRoot 或依赖；Linux install/node-path 为本机启动状态，不导出。

补丁不再按具体版本号拦截，但仍检查目标结构和加载行为。原生更新或 npm 安装本身不属于构建回滚事务；构建失败恢复编译状态，恢复插件还须用旧锁文件重新安装。恢复数据库必须使用该次私密在线备份并先停止相关进程，不能把普通配置 Restore 当成依赖或数据恢复。

任务代理管理与 Fleet 可用不等于新任务授权。安装后维护入口继续要求真实用户对权限和核心机制的明确维护意图，普通技能使用普通文件工具维护。仓库同步、提交及发布不属于安装后的 Agent 职责。
